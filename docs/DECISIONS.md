# Design decisions and deviations from the spec

| Decision | Why |
|---|---|
| Node/TypeScript + `node:sqlite`, no dependencies | Runs the same code in Replit-style environments and in an Electron main process; no native modules to rebuild. Trade-off: `node:sqlite` is experimental and has no SQLCipher. The spec's Rust/Tauri core is superseded by the Electron decision. |
| Server (SQLite) is the source of truth for open bills; no `cart_draft` table | Every cart edit is already persisted in `sale_order` and `sale_order_line`, so a crash or reload restores from there. |
| Cart/finalize commands log a compact reference; replay rebuilds the response | A 1,000-line cart logged in full would write ~150 MB to `command_log` while building. Measured: 48 KB. |
| Cancel is allowed only for the same IST day AND while the invoice's shift is still open | Keeps the drawer count consistent. Otherwise use a credit note. |
| Credit notes scale each tax component; the final return of a line takes exactly the remainder | Prevents paisa drift across partial returns. A full return also returns the original round-off. |
| Device prefix is 1 to 2 characters | `A1C/26-27/000001` (credit note) must stay within 16 characters. |
| Place of supply defaults to the outlet state; a buyer GSTIN switches the bill to IGST when the state differs | B2B later needs no schema change. |
| Discount approval stores the approved ratio | A cashier cannot get a small discount approved and then inflate it by removing items. |
| Failed approval PINs are recorded after the transaction rolls back (`afterRollback`) | Otherwise brute-forcing a manager PIN through a failing command would never lock out. |
| Daily summary is incremental and verified against a full recompute | Fast reports, with a repair tool (`recomputeDailySummary`). |
| Journal days older than 2 are gzipped | 2.5 KB to ~130 bytes per bill. |
| Yearly archive files from the spec are not built yet | At 0.9 KB per bill the active DB stays under ~0.5 GB per year at 1,500 bills/day; build it when a shop needs it. |
| Windows spooler RAW printing goes through a short-lived Windows PowerShell 5.1 process that calls winspool.drv (P/Invoke) | Zero dependencies and no native module to rebuild for each Electron version; PowerShell 5.1 ships with every Windows 10/11. The script is constant and passed as `-EncodedCommand`; the printer name goes in an environment variable and the bytes on stdin, so no database value reaches a command line. A failed write calls `AbortPrinter` so a retry never adds to half a receipt. Cost: about 0.65 s per job on a developer PC (compiling the helper each time); measure on a low-end PC. Risk: some antivirus products flag `-EncodedCommand`. If either is a problem, keep one helper process alive or move to a native module in the Electron host. |
| `openDb` closes the handle when the database is refused (checksum, too-new schema) | Windows keeps open files locked, which would block replacing the file during a restore. Found by the first test run on Windows. |
| The UI in `ui/` is a rebuild of the Lovable "Tiffin POS" prototype, not a copy | Only its compiled, minified site was reachable (no source maps; the Lovable preview link needs the owner's session). The prototype also calculated GST in the browser and kept data in localStorage, which breaks rules 2 and 3. The rebuild keeps its design tokens, layout and screens and talks to the backend. If the Lovable source turns up (GitHub sync or download), compare designs and keep this data layer. |
| UI: React 19 + Vite + Tailwind 4, hash routes, relative asset paths, fonts bundled | Hash routes and `base: './'` let the same build load from the dev server or `file://` in the Electron host. Fonts are bundled because shop PCs are often offline. The UI has its own `package.json`, so the backend keeps zero runtime dependencies. |
| Dev UI reaches the backend through the Vite proxy | The backend's Host allow-list and no-CORS policy stay unchanged. |
| `src/seed.ts` detects "run directly" with `pathToFileURL` | The old file-URL string comparison never matched on Windows, so `npm run seed` silently did nothing there. |
| Inventory is an append-only ledger (`stock_movement`) plus a cached balance | Same pattern as invoices: nothing is edited or deleted (triggers), corrections are new rows, and `verifyStock` recomputes balances from the ledger (deep health check). |
| Bills deduct recipe ingredients inside the finalize transaction; stock never blocks a bill | A bill is whole or absent including its stock. Negative balances are allowed and flagged "Count needed" so a busy counter is never stopped by a stock mistake. |
| Cancelling a bill restores its stock; a credit note does not | Cancel means the bill should not have happened (same day). A credit note is a refund for food already made, which is usually thrown away. **Needs owner confirmation.** |
| Purchases are immutable; mistakes are voided and re-entered | Keeps an audit trail of what was bought. A void reverses the stock and resets the last cost to the latest remaining purchase (or the opening cost). |
| Purchase amounts are `mulDivRound(qty_milli, unit_cost, 1000)`; a preview endpoint returns them | Integer paise, half up, computed once in the backend; the UI only displays them (rule 2). |
| Stock changes are journaled (`stock` entries, and stock rows inside `invoice`/`cancel` entries); replay orders item snapshots by `version` | A lost database is recoverable with stock intact. Version counters, not timestamps, because two changes can share a millisecond. Recipes are configuration and, like the menu, are not journaled. |
| Item names are unique on the menu (case-insensitive); the CSV upload refuses names already on the menu | Two items with the same name confuse the cashier and the reports, and uploading the same file twice used to create duplicates silently. Edit an existing item instead. |
| Food type is veg, non-veg or not set ("Not food") | Maps to the existing nullable `is_veg`; no schema change. Egg counts as non-veg. A distinct egg mark would need a migration. |
| The CSV veg column is strict, and tax_percent is parsed as digits | A typo like "veggie" used to become non-veg without warning; now the row is rejected. The rate is converted to basis points without floating point (rule 1). |
| A category can be deleted only when it has no items; order is saved for all categories in one command | Nothing on the menu loses its category by accident, and a reorder is atomic. |
| Menu photos are files in `data/images`, named by the SHA-256 of their bytes; the database stores only the name | Keeps the billing database small and fast; identical photos are stored once; a name can never point at different content, so photos are cached forever. |
| The browser resizes photos (640 px, WebP) before upload; the backend checks the real format from the bytes | No native image library in a zero-dependency backend. Re-encoding drops camera metadata (GPS). SVG is refused because it can carry script. |
| Photos are served without sign-in, by exact name only | `<img>` tags cannot send the bearer token. Menu photos are not sensitive, the API is bound to 127.0.0.1 with the Host check, and the strict name pattern means no other file can be read. |
| Photo files are written before the database change, and unused ones are deleted at startup after a day | No disk I/O inside the transaction. A failed save leaves at most an orphan file, which startup cleans up. |
| Photo backups: one shared `images` store per backup folder, filled incrementally; pruned only when no remaining backup refers to a photo | Photos never change (named by their hash), so copying each once is enough and 70+ backups do not multiply them. If any backup in the folder cannot be read, nothing is pruned. |
| A missing photo never fails a backup or a restore; it is reported | The bills are what must be recoverable. Photos can be uploaded again. |
| Restore is a command (`npm run restore`), run with the POS stopped | Swapping the database under a running server is risky. The command checks the backup first, keeps the current database in `pre-restore-<time>/`, restores the photos, replays the journal so no later bill is lost, and puts the old database back if anything fails. A restore screen can call the same steps later. |
| Bluetooth printers print through their Windows COM port (Serial Port Profile), using System.IO.Ports.SerialPort in Windows PowerShell 5.1 | Paired Bluetooth printers appear as an outgoing COM port; no native Bluetooth stack or Node module needed. Same safety rules as the spooler: constant script, port and settings in environment variables, bytes on stdin, timeouts kill the helper. |
| Migration 3 rebuilds the printer table (adds the `serial` transport) with foreign keys off | SQLite cannot change a CHECK constraint in place. The runner switches foreign keys off before BEGIN (it is a no-op inside a transaction), runs `PRAGMA foreign_key_check` before commit, and always switches them back on. |
| Printer discovery: Windows printer and COM port lists (PowerShell/CIM), and a TCP scan of the PC's own private /24 on port 9100 | The shop picks a printer instead of typing names, ports or IPs. The scan never leaves private ranges, never sends data (connect only), and is manager-only. |
| A printer with print history is turned off, not deleted; turning one off moves its waiting jobs to FAILED | Print history stays linked; queued jobs would otherwise wait forever. The cashier sees them as failed and can reprint elsewhere. |
| Finalize reports what it queued to print (`print.warnings`) | A bill with no receipt printer used to print nothing silently. The bill is still saved; the cashier is told and can print on screen. |
| Browser printing uses the backend's receipt text (`/receipt`), rendered in a monospace block sized to the paper | One layout for thermal and on-screen receipts; works with any Windows printer or "Save as PDF" when no ESC/POS connection is set up. |
| Split payment and refund amounts are computed by the backend (`payment-check`, `credit-note/preview`) | Keeps rule 2: the UI never adds or scales money. The refund preview and the credit note share one function, so they cannot differ. |
| Driverless USB printing writes to the GUID_DEVINTERFACE_USBPRINT device (usbprint.sys) found with SetupAPI | Windows loads this class driver for every USB printer, even with no printer driver installed, so cheap thermal printers work the moment they are plugged in. The printer is stored as vendor:product[:serial], not a port, so another USB socket works. Migration 4 adds the `usb` transport (same table rebuild as 3). |
| Plug and play is on demand: the billing screen asks every 10 s; the backend scans at most every 15 s and only then | No background PowerShell when nobody is looking. A printer is offered once; "Not now" is remembered in settings. Setting one up needs a manager (a cashier gets the approval dialog), and a test page prints at once. |
| Desktop app: Electron 44 with the backend in a `utilityProcess` | Electron 44 ships Node 24.21, the version the backend is tested on, so `node:sqlite` and the zero-dependency backend run unchanged (bundled to one file by esbuild). A separate process keeps a backend crash from taking the window down and lets the host restart it. |
| The window loads `app://pos`, and the main process forwards `app://pos/api/*` to the backend | Same origin for UI and API: no CORS change, and the UI build is identical to the browser one. The page has no Node and no preload; a forwarder is a smaller attack surface than an IPC bridge that exposes every command. Forwarding uses Node's fetch, so a system proxy never sees bills; streams (live events) pass through. |
| Per-launch secret on the backend (`X-POS-Secret`), random loopback port | Other programs and other Windows users on the PC cannot call the API (they would still need a PIN, but now they cannot even reach it). Compared in constant time; removed from the environment before print helpers start. Optional, so `npm start` and the browser UI are unchanged. |
| Data in `%LOCALAPPDATA%\TiffinPOS`, per-user NSIS install, uninstall keeps data | No administrator needed (shop PCs often have none). Local, not roaming AppData, so a domain profile never syncs a live SQLite file. Uninstalling or reinstalling can never delete bills. Trade-off: one Windows user per POS; a PC shared by several Windows users would need a per-machine install and a shared data folder. |
| Updates install only when the POS is closed | A restart in the middle of a rush is worse than running an old version for a day. |
| SQLCipher is not done in the desktop app yet | `node:sqlite` cannot open encrypted databases. Options: a SQLCipher build of better-sqlite3 (native module, rebuilt per Electron version) or Windows BitLocker on the shop PC. Needs a decision, a recovery-key design and a migration of existing databases. |
| USB printers on WinUSB are printed through winusb.dll, not by changing their driver | A printer whose driver was swapped to WinUSB (Zadig/libwdi, some vendor kits) has no usbprint interface, Windows printer or COM port, so it was invisible. Putting back usbprint needs an administrator; shop PCs often have none. Printer-class devices (USB class 07) on WinUSB are found from the registry (Service, CompatibleIDs, DeviceInterfaceGUIDs, readable without admin) and written to the first bulk OUT endpoint with a 10 s pipe timeout. A probe mode opens the device without sending bytes, for tests on real hardware. |
| Bill designs are data files (`.tiffinreceipt`, JSON), not code or HTML | A design can only arrange values the backend computed, so it can never change an amount (rule 2) or run anything. Strict checking (unknown keys and placeholders refused) catches typos before a shop sees them. JSON keeps the file editable in any text editor and safe to send by WhatsApp. |
| A design must contain the GST bill parts; the safety marks and the cut are always added by the renderer | A shop cannot upload a "bill" without number, date, GSTIN, items, GST or total, and cannot hide SAMPLE, CANCELLED, DUPLICATE or CREDIT NOTE. What exactly a bill must show is still a CA decision. |
| Stored in settings; a stored design that stops parsing falls back to the standard layout | Backups carry the design. Printing never fails because of a design file. |
| Item tables size themselves | Fixed columns grow to their widest value and the name takes the rest; below 12 characters for the name, items print on two lines. A design written for 80 mm still prints correctly on 58 mm. |
| Store details are versioned (`outlet_version`, append-only, migration 5) | A tax invoice must show the seller details valid when it was issued. Bills read the version in force at their issue time, so reprints never change after an edit. Two edits in one millisecond get consecutive times. |
| A new GSTIN must pass the check digit and match the store's state | A typo would print on every bill. A GSTIN from another state would change CGST/SGST to IGST, which needs a new setup, not an edit. An unchanged GSTIN is not re-checked, so stores set up with a format-only check are not blocked. |
| The bill logo is converted to 1-bit dots in the browser and stored in settings | The backend has no image library (zero dependencies). The owner sees exactly what will print and can adjust darkness and size. At most 384 x 240 dots (58 mm printable width); centred on 80 mm by padding the raster rows. Not versioned: a logo is not a legal part of the bill. |
| The default bill is a design file (Classic), not hand-written code | One renderer for every bill; the default can be copied and edited like any design. The earlier layout is kept as templates/receipt/standard.tiffinreceipt. |
| Active user names are unique (case-insensitive) | The sign-in screen lists people by name; two "Ravi"s would make a cashier sign in as someone else. A deactivated person's name can be reused; reactivating them then needs a different name first. |
| An owner cannot deactivate themselves or change their own role | Prevents locking the shop out of Settings by mistake. Another owner can do it; the last owner is always protected. |
| Online orders are off by default; one switch decides online or offline mode | A shop that never takes online orders keeps a POS with no internet dependency. Everything that would connect out for orders checks isOnlineMode(); ODS is hidden (menu and route) when off. Channel choices are kept when switched off. |
| Online orders ship as a signed add-on with its own installer | The owner wanted the online modules separate from the POS. Ed25519 signature + per-file SHA-256 + minimum POS version; only checked bytes are run; failures switch the add-on off and never stop billing. Add-ons get a HostApi instead of importing POS code (no duplicate module state). |
| Add-on screens share the POS React via window.__POS__ and ship their own Tailwind CSS | One React and one session; the POS stylesheet only contains classes the POS uses, so an add-on built later brings its own utilities, generated with the POS theme. |
| Map tiles and address search go through the POS backend | The page keeps its strict CSP (no outside hosts); requests happen only in online mode; tiles are cached on disk; OpenStreetMap/Nominatim are used lightly with an identifying User-Agent (switch to a paid provider at scale). |
| Serviceability rules live in contract/ | The hub will quote and accept orders with exactly the same zone, minimum order, free-delivery and opening-hours logic as the POS settings screen. Distances are straight-line in v1. |
| The order hub is a small Node + SQLite service (hub/), not PostgreSQL yet | Same zero-dependency style as the POS and testable on one PC; one process per database. Move to PostgreSQL when hosting (phase 4) if more than one process is needed. |
| Online orders are billed as normal POS bills through host.billing (src/services/onlineBilling.ts) | One GST, numbering and stock path for every bill; idempotent per channel + order number; a failed step cancels its draft. |
| Delivery and packaging fees are bill lines on hidden system items (SYS-DELIVERY, SYS-PACKAGING) with a chosen GST group | GST on fees appears on the bill and in GST reports without a new bill structure; the hub prices them with the same computeInvoice, so the customer's total equals the bill. Rate to confirm with the CA. |
| The POS connector uses an outbox table (ods_outbox) | Answers to the hub (received, accept, reject, status) are stored with the bill in one step and sent later, so an internet drop or a restart never loses them (F2, F3). |
| Road distance = OSRM on the hub when configured, else straight line x road factor (default 1.30) | No paid routing needed to start; a per-store factor corrects for local roads; a measured distance is used as soon as a routing server is set. |
| Add-on loader hardening: folder = id, anti-rollback, SQL limited to own tables | Cheap protections against mistakes and replaying an old faulty package; not a sandbox (a signed add-on is trusted). Human review still required (docs/ADDONS.md). |
| Pairing over plain http only for a hub on the same PC | The device key travels on that connection. |
| Kitchen tickets print only what the kitchen has not had (kot_line per order), split by prep station | A KOT can go from the cart before billing, so billing must not print it again; additions print as ADD-ON tickets and removals as CANCEL lines instead of whole new tickets. Prep stations are records (ids), not free text, so renaming one never breaks a printer. Three designs (customer, prep station, online) as the owner asked; the standard customer KOT copies the shop's sample. No dine-in or table number: the POS has no tables. |
| Swiggy and Zomato through UrbanPiper, received by the hub (not the shop PC) | UrbanPiper sends orders to a web address on the internet; the hub already turns orders into the contract shape and sends them live to the POS, so the POS needs no new connection. The UrbanPiper key stays on the hub. Orders are priced from the published menu at the channel price (the POS bill), with the platform's own total beside it; the GST treatment of these bills needs the CA. |
| The owner chooses the map in Settings > Serviceability: the free OpenStreetMap map (default), or Google road / satellite / satellite with roads with the owner's key | The owner wanted Google's map and listings, and later the free map back as a choice even with a key (ODS 1.0.8), plus satellite views; the key box moved into the Map card and the API keys section was removed. The key is kept in the POS backend only (settings named "..._key" are never listed); Google tiles are fetched through the POS and not kept on disk (Google's terms); Place Details asks only Essentials fields (cheapest tier). Without a key the free map still works. |
| Free place search uses Photon, not Nominatim, for suggestions | Nominatim's policy forbids type-as-you-go; Photon is built for it. OpenStreetMap lacks many Indian restaurants, so Google Places / Ola Maps are offered with the owner's own key, and pasted Google Maps coordinates always work. |
| Staff sign in with mobile number + PIN; the lock screen (lock button) asks the PIN only | The owner asked for it: the name list is gone from the sign-in screen, and the person who was billing gets back in quickly. Numbers are unique (deactivated users keep theirs). The backend still accepts a user id with the PIN so existing staff without a number are not locked out after the update. |
| A coupon is the bill discount (amount after any % cap), checked at apply and at payment | Tax works exactly as for a manual bill discount (apportioned over lines). The owner approved the coupon when creating it, so it does not count against the cashier's discount limit; line discounts still do. A coupon that stops applying (bill below the minimum, switched off, used up) is shown on the bill and blocks payment rather than silently charging more. Uses = paid, not-cancelled tax invoices. Needs a human (CA) review like any discount. |
| Android runs the same Node backend (Termux's Node 24 build inside the APK), not a rewrite | One codebase for tax, numbering, backups and every safety rule (synchronous=FULL, triggers) on both platforms; the full test suite runs on Android. Costs ~30 MB per APK. Alternatives rejected: React Native/Flutter (would need a second backend), SQLite in WebAssembly (weaker durability, rule 11). |
| The Android window reaches the POS through a gatekeeper with a private cookie | Other apps share the device's loopback network; the cookie lives only in the app's WebView, so they cannot use the POS. The backend itself is unchanged (still guarded by its launch secret). |
| Channel prices: the POS computes them (contract `channelPrice`: own price, else POS price + % to the nearest rupee) and bills at them | The customer's total and the GST bill must match. The add-on passes `channelPrice` to `billOnlineOrder`; `addLine` accepts it only from code (HTTP bodies refuse unknown fields), so no screen can set a price. Needs a CA check like any pricing change. |
| Menu photos are compressed in the browser: longest side 1024 px, high-quality resize, WebP at 90% | Measured on real 3840 x 2400 photos in Edge: the browser's default resize was the main loss (PSNR 31-49 dB against a careful step-by-step resize); the high-quality resize matched it. WebP 90% kept 38-46 dB (no visible difference) at 15-76 KB per photo, about 95% smaller than the originals. 1024 px (was 640) keeps photos sharp on customers' phones. Single and bulk uploads share ui/src/lib/photo.ts; the backend still only checks type and size (1 MB). |
| Payment machines ship as an add-on (id edc), not in the POS core | Shops without a card machine install nothing extra; machine code updates without a POS release. The POS offers general tools (finalize a bill, a bill's total, manager approval, PowerShell, a payment guard) and two screen slots (checkout, bill panels) that other payment add-ons can use too. |
| Payment machines: one Connector per company and connection; the bill is saved only on approval, through the normal finalize | The counter, settings and daily match never depend on a company. A machine payment is a terminal_txn (not a financial record) until approved; then finalize records it as an ordinary CARD/UPI payment with the approval code as reference. Paytm and Pine Labs first (public billing-integration documents); PhonePe and Razorpay can follow as connectors. |
| Anything unclear from a machine is "UNKNOWN", never "FAILED" | A lost answer may hide an approved payment; calling it failed would invite charging the customer again. The cashier checks the machine and pays by hand with the slip if it was approved. |
| Paytm by cable uses Paytm's own library through PowerShell; it is not bundled | Paytm publishes no cable protocol, only a library without a licence file; each shop downloads it. PowerShell 5.1 loads .NET libraries, as the printing helpers already do. |
| A wrong payment mode is fixed by an immutable payment_correction row, not by editing the payment | Payments stay immutable (RULES 5). The view payment_effective gives each payment's corrected mode; reports, X/Z and daily totals read it, the bill view shows both. Only for the open shift (a closed shift's cash count is final), with a reason and a manager; journaled so a restore keeps it. Needs CA review. |
| Rupee sign and Indian scripts print as pictures drawn by the print queue | Finalize must stay one transaction without I/O, so the bill only carries a marker (ESC ~ U + JSON) for such lines; the queue draws them just before sending (Windows: GDI+ in a constant PowerShell script, Android: the app's Canvas) and falls back to the old text ("Rs", "?") when it cannot. No font engine is bundled: the operating system already shapes Hindi correctly. |
| Never signed out or locked by the POS itself; a lock button instead (POS 0.3.10) | The owner asked for it: a busy counter must not lose its cashier to a timer, a close or a crash. A shared counter is protected by the lock button, whose lock survives restarts. Trade-off: an unattended, unlocked POS stays usable by anyone at it. |
| Sign-ins survive restarts; only a hash of the token is stored | An update, crash restart or restore no longer signs the cashier out mid-shift. The inactivity lock still applies after a restart; unused sign-ins expire after 12 hours. |
| "Not available today" is a date on the item, not a switch | It clears itself the next day (IST) without a job; online orders placed a moment before still bill (allowUnavailable, code only). |
| Online backups go to our own Tiffin backup server (built into the order hub), not Google Drive or S3 | The owner's choice: shops need no account of their own. The POS pairs with a one-time code (like online orders), uploads the newest verified backup gzipped with its SHA-256 every 1-24 hours (default 3) and the photos it uses; the server keeps the newest 30 per store on disk. Off until connected (offline is the default); billing never waits for an upload. |
| Online backups are not encrypted with a separate password | The owner's choice ("No extra password"): simpler, and a forgotten password can never lock a shop out. They travel over https and are readable on the server, so the server must be secured and its access limited. Revisit before hosting it for many shops. |
| Restore from the screen stages the backup, then the backend restarts itself in place (same port) | Swapping the database under a running server stays forbidden. startBackend applies a staged restore before opening the database, so the desktop window and the Android gatekeeper need no changes. A restore that fails is tried once only, recorded, and the previous database is put back. The owner types their PIN again. |
| After a restore the journal is replayed only if the backup and the current database share a device | Restoring onto a new PC that was set up first must not mix that PC's test bills into the shop's records: its database and journal are kept aside instead. Same shop: later bills come back, numbering continues. |
| The Windows installer packs the app as zip (deflate), English-only Chromium strings, no WebGPU shader compilers | Built for low-end shop PCs: a silent install on one CPU core took 41-53 s with the default LZMA package and 21-26 s with zip after trimming (296 MB, 18 files instead of 370 MB, 74 files). Costs a larger installer (~131 MB instead of ~112 MB) and no differential updates (each update downloads the whole installer). Revert with `useZip`/`differentialPackage` in desktop/electron-builder.config.cjs if update downloads matter more. |
| Menu sync filters the hub's single menu per channel (`channels`, `prices` on each item) | One published menu, one version; the hub serves and prices each channel's view and refuses items a channel does not list. |
